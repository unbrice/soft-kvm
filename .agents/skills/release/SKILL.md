# Release

A commit to master that changes `CHANGELOG.md` triggers `stable.yml`. It reads
the version from the top `## vX.Y.Z` heading, tags that commit and builds the
release from the tag, so Go stamps the version into the binary. It fails without
tagging unless the commit's non-Markdown files match those of the commit
`unstable` was built from, the build the user tested. This skill writes the
changelog section and ships it; it never tags, edits a release or pushes
anything but the changelog change.

## Procedure

### 1. Start from `trunk()`

```sh
jj git fetch
jj new 'trunk()'
```

Always, even when `@` is empty: anything below `@` ships with the changelog.

### 2. Check that `unstable` is current

The `unstable` tag must point at the newest `trunk()` commit that changes a
non-Markdown file (`unstable.yml` does not trigger on commits that change only
Markdown):

```sh
jj log -r 'latest(::trunk() & files(~root-glob:"**/*.md"))' --no-graph -T 'commit_id ++ "\n"'
gh api repos/:owner/:repo/git/ref/tags/unstable --jq .object.sha
```

If they differ, read the latest `unstable.yml` runs:

```sh
gh run list --workflow unstable.yml --branch master --limit 3 --json databaseId,status,conclusion,headSha,url
```

- **Queued or in progress:** `gh run watch <id> --exit-status`, then compare
  again.
- **Failed:** `gh run view <id> --log-failed`; report the cause and stop.
- **Neither:** report the mismatch and stop.

### 3. Collect what changed

The next version is the newest `v*` tag with its minor bumped:

```sh
gh api repos/:owner/:repo/git/matching-refs/tags/v --jq '.[].ref' | sed 's|refs/tags/||' | sort -V | tail -n1
```

- **No tag yet:** the next version is `v0.1.0`. Write a short first-release
  summary of what soft-kvm does, from `README.md`, rather than the history.
- **Otherwise:** `v0.X.Y` → `v0.(X+1).0`. Resolve the tag's commit with
  `gh api repos/:owner/:repo/git/ref/tags/<prev_tag> --jq .object.sha` (jj may
  not have imported the tag) and read the range:
  ```sh
  jj log -r '<prev_sha>..<unstable_sha>' --no-graph -T 'commit_id.short() ++ " " ++ description ++ "\n---\n"'
  ```
  Skip the previous `docs: changelog for ...` commit. If nothing else is left,
  report that nothing has landed since `<prev_tag>` and stop.

### 4. Write the section

If the top `## v` heading in `CHANGELOG.md` is already `<next_tag>`, an earlier
changelog commit reached master and `stable.yml` failed on it: revise that
section (today's date, the full range) instead of adding a second one. The
revised commit triggers `stable.yml` again.

Otherwise add `## <next_tag> (YYYY-MM-DD)` directly under `# Changelog`.

Write concise bullets grouped by kind (new, changed, fixed), for someone running
soft-kvm, not for its developers. Run `just fmt`.

### 5. Review it with the user

Show the drafted section and the `unstable` SHA it releases, and ask whether it
needs improvement. Apply the requested edits, run `just fmt` and show the
section again. Repeat until the user approves it as is. Nothing past this step
runs without that approval.

### 6. Describe and ship

```sh
jj describe -m "$(printf '%s\n\n%s\n\n%s' \
  'docs: changelog for <next_tag>' \
  'Generated by LLM, reviewed by committer.' \
  "Signed-off-by: $(jj config get user.name) <$(jj config get user.email)>")"
just check
```

Then ask for approval to run `just ship @`. GitHub merges the PR on its own, and
the commit it lands on master triggers `stable.yml`, which tags and builds the
release; the user's machine can be off. To follow it:

```sh
gh run list --workflow stable.yml --limit 1
gh run watch <id> --exit-status
```

`stable.yml` fails without tagging if a commit changing a non-Markdown file
landed after the `unstable` build. Re-running that job compares the same commit
and fails again; once the new `unstable` build lands, run this skill again and
step 4 revises the section.
